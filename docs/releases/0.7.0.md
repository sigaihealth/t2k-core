# Core 0.7.0: exact evidence claim-set evaluation

`@t2kai/core@0.7.0` adds opt-in equality checks for supporting and considered
evidence claim sets in experimental graph evaluation. A case can now reject
unexpected evidence as well as missing evidence. Existing cases keep their
required-subset assertions.

```bash
npm install @t2kai/core@0.7.0
```

## Matching and preflight

An evaluation case may add
`expected.evidence.claimSetMatching: { supporting: "exact", considered: "exact" }`.
Either role can be selected independently. Exact matching compares the complete
unordered claim-id set; an empty expected array requires an empty actual set.
An omitted role retains required-subset behavior.

Supporting means `result.supportingClaimIds`. Considered means every claim in
`result.evidence`, including claims that also support the answer, explain
exclusions, or carry unresolved evidence. Row and exclusion assertions keep
their existing required-subset semantics; this extension does not assert exact
derivation counts, exclusion counts, trace contents, or issue codes.

Preflight rejects empty matching declarations, unsupported roles or modes,
duplicate expected ids, and contradictory labels before execution or a provider
call. Exact supporting labels must contain required row-support claims. Exact
considered labels must contain required supporting, row, and exclusion claims.
Unresolved answers still cannot claim answer support. Structurally consistent
labels still require independent review.

## Authoring and diagnostics

`GRAPH_EVALUATION_CLAIM_SET_MATCHING` advertises the `supporting` and `considered`
roles. `graphGenerationInstructions(requirements?, trainingCases?)` appends
`GRAPH_GENERATION_EXACT_EVIDENCE_INSTRUCTIONS` only when a development case opts
in, allowing hosts to preflight the same instruction bytes as generation.
Candidate repair preserves the reviewed matching modes and labels. Development
failures report missing and extra claim counts with bounded samples.

Final labels remain outside generation and repair requests. Adding exact matching
after observing a final outcome does not create a fresh independent final suite.

## Compatibility and adoption

This is an additive opt-in extension of `t2k.graph-evaluation.v2`. Cases without
the field retain their normalized suite and evaluation hashes, result semantics,
and generation request bytes. Tests preserve recorded published Core 0.6.0
hashes and cover independent role selection, complete and unresolved answers,
empty sets, contradictory labels, missing/extra evidence, and retained repair
constraints.

Older evaluators reject the new field. Hosts must detect both the required
matching capability and a trusted executable build before accepting an exact
contract. Adding or removing matching modes requires newly reviewed labels and
a newly pinned contract; historical receipts must retain their original meaning.

The package's executable build identity changes. Hosts must verify the registry
artifact and provenance, establish the new trusted host binding, and revalidate
active functions while preserving their original acceptance evidence. The graph
artifact and result versions and interpreter operators are unchanged. Graph
reasoning remains experimental, and Core does not authorize activation, source
mutation, or downstream actions.

This release publishes Core only. The published `@t2kai/mcp@0.4.0` and
`create-t2k@0.5.0` continue to use Core 0.5.0. Their source dependency/template
pins track Core 0.7.0 for repository package checks, but adopting those changes
requires separate new package versions and signed release tags. No MCP or
scaffolder release tag is part of Core 0.7.0.
