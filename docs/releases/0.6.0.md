# Core 0.6.0: bounded entity distinctness

`@t2kai/core@0.6.0` adds explicit entity distinctness to the experimental graph
runtime. A crew reached through several eligible site or route paths can now
contribute its capacity once. Two different crews with equal capacity both
contribute. Core 0.5.0 preserves path multiplicity and cannot express this query.

```bash
npm install @t2kai/core@0.6.0
```

## Operator and evidence semantics

`{id, op: "distinct", from, binding}` accepts entity-binding collections before
projection. It groups by the selected binding's exact graph entity id, keeps
only that binding, and emits canonical id order. Other aliases are dropped so
the runtime cannot silently choose one path as representative of the entity.
Constraints involving those aliases must run before distinct.

Supporting claim ids are unioned across every incoming path. Every unresolved
issue is preserved and canonically deduplicated. A clean path does not erase a
disputed, stale, or unsupported alternate path. Exclusions and considered
evidence remain in the execution receipt. A resulting unresolved answer remains
`needs_review` with `value: null` and no answer-supporting evidence.

The existing intermediate row budget still applies before collapse. Distinct
charges its step, input rows, every merged claim and issue, and deterministic
sort allowances. It never truncates a result to fit the budget. Numeric
aggregation uses the existing finite-number semantics; empty count and sum are
zero. Grouping, ranked output, arithmetic, disjunction, implicit identity
resolution, and calls to other functions remain unsupported.

## Reviewed authoring

`GRAPH_SYNTHESIS_CAPABILITIES` now includes `distinct`. Generation requires both
the `distinct` capability and `multiplicity: "distinct"`; inconsistent
declarations fail before any provider call. The provider schema offers the new
operator only for that explicit declaration. Generated programs that violate
reviewed multiplicity receive repair diagnostics even when a small development
suite happens to pass. Contracts without requirements preserve path multiplicity
and cannot silently opt in through a custom provider response.

`graphGenerationInstructions(requirements?)` lets hosts preflight the exact
instructions Core generation will dispatch. Distinct-only instructions are
appended for opted-in contracts; legacy instructions and schemas are unchanged.
Final evaluation labels remain outside candidate generation and repair.

## Compatibility and validation

The artifact remains `t2k.graph-function.v1` and the interpreter remains
`t2k.graph-runtime.v1`. Existing programs retain their function hashes, result
semantics, and complete execution receipts. Verification compared all 15
existing Harborlight receipts, the compiled function, and legacy generation
instructions and schema byte for byte. New tests cover typed binding flow,
equal-valued entities, alternate-path uncertainty, evidence union, empty
aggregates, resource bounds, engine-independent sort accounting, explicit
generation opt-in, and declaration/schema checks.

The package's executable build identity changes. Hosts must validate the
provenance-backed registry artifact, establish a new trusted host binding, and
revalidate existing active functions while preserving prior acceptance evidence.
Core does not authorize activation, source mutation, or downstream actions.

This release publishes Core only. The already published `@t2kai/mcp@0.4.0` and
`create-t2k@0.5.0` still use Core 0.5.0. Their source dependency/template pins now
track Core 0.6.0 so repository package checks exercise the exact new runtime;
those source changes require separate versioned releases before consumers adopt
them. No MCP or scaffolder release tag is part of Core 0.6.0.
